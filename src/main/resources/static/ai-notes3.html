2. QueryPlan 是什么

QueryPlan 不是 SQL，而是 AI 对“应该怎么查”的结构化描述。

public record QueryPlan(
    String table,
    List<String> select,
    List<QueryFilter> filters,
    String orderBy,
    String direction,
    Integer limit
) {
}

每个字段的意义：

字段作用
table目标表
select要返回哪些字段
filtersWHERE 条件
orderBy排序字段
directionASC / DESC
limit最大返回条数

3. QueryFilter

public record QueryFilter(
    String field,
    String operator,
    String value1,
    String value2
) {
}

它表示单个查询条件，例如：

{
  "field": "created_at",
  "operator": "TIME_BETWEEN",
  "value1": "11:00",
  "value2": "13:00"
}

对应用户表达：

查询中午时段的消费记录

4. 为什么不直接让 AI 生成 SQL

这次设计最重要的一点是：

AI 只负责生成“查询计划”，不直接决定最终 SQL。

如果直接让模型生成：

SELECT ...
FROM ...
WHERE ...

程序很难系统性检查它是否：

  • 用了不存在的表
  • 用了不存在的字段
  • 执行了 UPDATE / DELETE
  • 返回过多数据
  • 拼出了危险 SQL

而 QueryPlan 可以先被 Java 校验：

AI
 ↓
QueryPlan
 ↓
Validator
 ↓
合法才允许继续
 ↓
MyBatis / jOOQ
 ↓
真实 SQL

5. AiService 的变化

之前 getData() 返回：

String

现在改为：

QueryPlan

核心变化：

public QueryPlan getData(String question)

System Prompt 也从“选择表并读取结构”，进一步升级成：

你负责根据用户问题生成数据库查询计划。

6. Prompt 中新增的约束

规则：
- 只能使用给出的业务表
- 必须先调用 getTableSchema 获取真实字段
- 不允许创造不存在的字段
- 只允许查询，不允许 INSERT、UPDATE、DELETE
- limit 最大为 100
- operator 只能使用：
  EQ, GT, GTE, LT, LTE, BETWEEN, TIME_BETWEEN, LIKE

这几个规则分别在解决：

规则目的
只能使用给出的业务表限制表范围
必须先调用 getTableSchema强制基于真实 Schema
不能创造字段防止 AI 猜字段
只允许查询禁止写操作
limit ≤ 100防止一次返回太多数据
限定 operator让后续执行层可以枚举和验证

7. 最关键的变化：content() → entity()

第二层主要为了观察 Tool 结果，所以之前：

.call()
.content()

第三层改为：

.call()
.entity(QueryPlan.class)

意义是：

LLM 返回结构化结果
        ↓
Spring AI 自动转换
        ↓
QueryPlan Java 对象

程序后面可以直接：

plan.table();
plan.select();
plan.filters();
plan.limit();

这一步非常重要，因为系统开始从“AI 返回文字”走向“AI 返回程序可以继续处理的数据”。

虽然最终输出变成 QueryPlan，但第二层 Tool 没有消失：

11. operator 为什么要自己定义

目前定义：

EQ
GT
GTE
LT
LTE
BETWEEN
TIME_BETWEEN
LIKE

这些不是 SQL 原文，而是系统内部的“查询操作符协议”。

后面 Java 可以安全映射：

EQ           → =
GT           → >
GTE          → >=
LT           → <
LTE          → <=
BETWEEN      → BETWEEN
TIME_BETWEEN → 时间范围
LIKE         → LIKE

这样就不会让 AI 自己传：

operator = "whatever sql fragment..."

第三层的结果不是“最终答案”，而是第四层执行查询的输入。

14. 为什么 Validator 不能省

即使 Prompt 已经写：

不允许创造字段
limit 最大为100

也不能完全相信 AI。

Prompt 是“告诉模型应该怎么做”；Validator 才是“程序强制保证只能这么做”。

Prompt
→ 软约束

Java Validator
→ 硬约束

这是后面 AI 数据查询安全性的核心。
